# Portable Workflow Recovery and v0.2.0 Design

## Context

The public repository and `main` branch remain at `v0.1.0`. The existing
`feature/v020-visual-fidelity` branch adds a tested visual-fidelity contract,
but the active host installation has moved further ahead: it also contains a
mission-animation contract, a patent/design-around contract, a mission
manifest validator, and routing tests. Those later files exist only in the
installed skill tree and are mixed with host-specific paths, local provenance,
and generated bytecode.

Version 0.2.0 will recover the portable engineering behavior into Git without
copying machine state into the public distribution. It will combine the
already-tested visual-fidelity work with mission-animation and patent-aware
design gates, while preserving the current third-party source locks.

## Goals

- Make Git the source of truth for every reusable `robotics-design` capability.
- Add portable mission-animation and patent/design-around workflow contracts.
- Add executable mission-animation manifest validation and repository tests.
- Keep host paths and installation metadata outside tracked public files.
- Allow an installer to create an optional, explicit host-runtime overlay.
- Publish one coherent `v0.2.0` release after review and cross-platform CI.

## Non-goals

- Do not update the three third-party source locks in this release.
- Do not migrate `cadpy` to the upstream `cadgen` 0.4.5 architecture.
- Do not claim pixel-level landmark detection, physics truth, patent clearance,
  hardware safety, or certification.
- Do not copy `__pycache__`, host timestamps, usernames, workspace paths, or
  private installation notes into the repository.

## Architecture

### Portable public core

The tracked `skills/robotics-design` tree owns only portable behavior:

- `SKILL.md` routes visual, mission-animation, and patent-aware work to their
  required contracts and artifact owners.
- `references/visualization-contract.md` continues to gate appearance-only
  image generation against deterministic topology and pose.
- `references/mission-animation-contract.md` requires one accepted trajectory
  and contact-state trace to drive every robot frame.
- `references/patent-design-around.md` requires claim-element mapping,
  equivalents/status uncertainty, architecture constraints, and a qualified
  counsel boundary.
- `scripts/validate_visual_manifest.py` remains the visual promotion gate.
- `scripts/validate_mission_animation_manifest.py` becomes the mission-motion
  promotion gate.

The design contract, validation gates, authority map, completion contract, and
agent metadata will reference these capabilities without embedding host paths.

### Optional host overlay

The installer accepts an optional CLI argument:

```text
--host-runtime-python <python-executable>
```

When present, the installer resolves the executable, requires it to be an
existing file, and writes
`robotics-design/references/host-runtime.md` inside the temporary staged skill.
The generated overlay records:

- the resolved Python executable;
- the resolved installation destination;
- that the file is generated host state rather than public source provenance;
- that project dependencies still belong in project-local environments.

The overlay is generated before the existing destination-filesystem
transaction is prepared. It is therefore installed or rolled back with the
rest of the suite. A dry run reports that an overlay is requested but creates
no destination or overlay. Without the argument, installation remains byte-for-
byte portable and no overlay is created.

`SKILL.md` will say to read `references/host-runtime.md` only when it exists.
The tracked `references/runtime.md` remains the cross-platform setup guide, and
`references/source-lock.md` remains public supply-chain provenance. Neither is
rewritten with host state.

## Data and control flow

1. Parse and validate the manifest and optional host-runtime argument.
2. Refuse any destination skill that already exists.
3. Download and normalize pinned third-party skills into the temporary stage.
4. Copy the portable local `robotics-design` skill into the temporary stage.
5. If requested, generate the host overlay inside that staged local skill.
6. Copy the complete install set to a hidden transaction directory beside the
   destination.
7. Publish every skill through same-filesystem renames, rolling back the whole
   set on a race or failure.

## Failure behavior

- A missing or non-file host runtime fails before network downloads begin.
- Overlay-generation failures leave the destination unchanged.
- Existing destination collision and ZIP traversal protections remain intact.
- A publish race rolls back every installer-owned target and removes the hidden
  transaction directory.
- Mission manifest validation returns actionable field errors and never
  promotes motion that lacks trajectory identity, required joint motion,
  contact phases, load cases, or review evidence.

## Testing

Repository tests will first fail against the current branch and then cover:

- routing to the mission-animation and patent contracts;
- rejection of hand-authored robot joint motion;
- claim-chart and counsel-boundary requirements;
- valid and invalid mission-animation manifests;
- optional host overlay generation, deterministic contents, and dry-run
  behavior;
- rejection of nonexistent host runtime executables;
- public hygiene for drive-letter paths, private markers, and bytecode;
- all existing visual-fidelity, manifest, installer, and transaction tests.

Release validation runs Python compilation, the full unit-test suite,
distribution validation, installer dry-run, real installation into a temporary
destination, official skill validation, and GitHub's Windows/Linux matrix.

## Release and follow-on work

The feature branch will be reviewed and merged to `main` as `v0.2.0`. The
release combines visual fidelity, traceable mission animation, patent-aware
architecture boundaries, and portable host overlays. The installed host copy
will not be treated as release evidence; a fresh install from the merged Git
commit is required.

After v0.2.0, upstream updates stay isolated:

1. Audit and update `ros2-engineering-skills` to 1.3.0 in a focused change.
2. Treat `text-to-cad` 0.4.5 as a separate compatibility migration because it
   replaces `cadpy` with `cadgen` and changes a broad artifact pipeline.
3. Leave `ros2-sim` pinned until its upstream head changes or a compatibility
   need is demonstrated.
